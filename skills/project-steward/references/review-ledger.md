# 待审台账（Review Ledger）

待审台账是员工、项目管家、大总管和用户共用的唯一事实来源，记录“谁在跑、产出了什么文件、文件现在等谁”。它解决的问题是：长任务里需要审的东西只留在某个 Session 的对话里，没人记得回去看。

台账是逻辑结构，存储与界面分开：

- **存储**：默认是一个目录下的 JSON Lines，按记录类型分文件（`workers.jsonl`、`files.jsonl`、`items.jsonl`、`events.jsonl`），只追加不改写，读取时按 `id` 取最新一条。需要多端访问时可换成同步后端，字段不变；载体写在 local rules，同一用户只用一个。
- **界面**：给用户看的事项与待审界面是原生 App，从台账读、把用户操作写回台账。不用多维表格或电子表格当用户界面：行列视图把文件、等级、等待时长和要用户决定的事挤在一起，可读性差。结构化表最多作为管家之间的机器侧镜像，不作为用户入口。

原生 App、看板和大总管都只读写这份台账，不另存一份。

## 记录类型

### 员工（worker）

| 字段 | 含义 |
|---|---|
| `id` | 稳定 ID |
| `project` | 所属项目 |
| `task` | 这个员工负责的任务，一句话 |
| `runtime` | `codex` / `claude-code` / `antigravity` / `openclaw` / 其他 |
| `session_id` | 运行时里的 Session 标识，用于续接 |
| `parent_session_id` | 派它出来的项目管家 Session |
| `model` | 实际使用的模型 |
| `status` | 见下方员工状态机 |
| `watch` | 用户是否提级盯这个员工（布尔） |
| `updated_at` | 最后更新时间 |

### 文件（file）

| 字段 | 含义 |
|---|---|
| `id` | 稳定 ID |
| `project` / `worker_id` | 归属 |
| `title` / `kind` | 标题；类型：方案、文档、PR、交接包、报告 |
| `location` | 文件路径、PR 链接或文档 URL；正文不进台账 |
| `ask` | 要审的人看什么、决定什么，一两句话 |
| `level` | `L0` / `L1` / `L2` / `L3`，含义见 `project-steward/SKILL.md` 的“汇报等级与待审文件” |
| `level_suggested_by_worker` | 员工建议的等级，供项目管家参考 |
| `status` | 见下方文件状态机 |
| `blocking` | 员工是否停着等这份文件的结论 |
| `decision` | 审核结论与意见原文 |
| `decided_by` | `manager` / `user` |
| `created_at` / `updated_at` | 时间 |

### 事项（item）

事项是“用户需要亲自做的一步”，是用户待办列表里的一行。

| 字段 | 含义 |
|---|---|
| `id` | 稳定 ID |
| `project` / `task` | 归属；个人事项可为空 |
| `title` | 用户要做的动作，动词开头，写清做完的标准，如“选定 onboarding 两个方案之一” |
| `source` | `user`（用户自己加的）/ `review`（由 `pending_user` 文件生成）/ `steward`（管家提出、需要用户动手的步骤） |
| `file_id` | `source` 为 `review` 时关联的文件 |
| `why_human` | 为什么必须由人做：拍板 / 授权或登录 / 付款 / 对外沟通 / 线下或亲手操作 / 目检 |
| `due` / `scheduled` | 截止与计划日期 |
| `status` | `open` / `done` / `dropped` |

#### 事项拆分门

只有需要人亲自操作或拍板的步骤才成为事项，AI 自己能完成的步骤一律不拆成事项：

- **算事项**：做一个产品或业务决定；审一份 L2 / L3 文件；登录、授权、付款、签字；回复或联系某个人；亲手拍摄、录制、线下操作；发布前目检。
- **不算事项**：检索、写代码、跑测试、改文档、生成图片、整理数据、写草稿等员工或管家能自己做完的步骤。它们是员工 Session 内部的进度，只更新员工状态和项目群里的阶段进展。
- 一件事拆完后若没有任何需要人做的步骤，就不生成事项，只保留任务本身。
- 新建 `steward` 来源的事项必须填 `why_human`；填不出来就说明它不该是事项。
- 同一件需要人做的事只生成一条，不把“打开链接、看第 3 节、回复意见”拆成三条。
- 不区分“里程碑”和“事项”，只有事项一种：多一个层级就多一份要用户确认的东西。任务的阶段进度写在任务和项目群里，不做成用户要勾选的里程碑。

### 事件（event）

只追加的流水：谁在什么时间把哪条记录从什么状态改成什么状态，以及原因。用于回放、对账和统计“等了多久”。

## 员工状态机

```text
排队 queued → 执行中 running → 等审 waiting_review → 执行中 running → … → 完成 done
                     ↘ 受阻 blocked（等外部依赖，写明解锁条件）
                     ↘ 失败 failed / 已交接 handed_off
```

- 进入 `waiting_review` 前必须已有至少一条 `blocking: true` 的文件记录；否则这是“丢在对话里”的等审，项目管家巡检时按遗漏回传处理。
- 会话结束钩子只能把状态改成“会话已停止，待核对”，最终状态由项目管家依据回传和五门证据判定。

## 文件状态机

```text
L0：留档 archived（不进入审核）

L1：待管家审 pending_manager → 管家通过 manager_approved
                             → 管家打回 manager_changes → 员工改完重新提交 → 待管家审

L2：待管家审 pending_manager → 已上报 escalated → 待用户审 pending_user
        → 用户通过 user_approved / 用户要改 user_changes → 管家下达给员工

L3（提级员工的文件）：直接进入 待用户审 pending_user；管家可附意见但不拦截
```

- 只有 `pending_user` 状态的文件会在用户的事项列表里生成一条 `source: review` 的事项；用户批复后该事项自动完成。
- 项目管家可以把 L1 改判为 L2；大总管不能改等级。
- 被新版本替代的文件标 `superseded` 并指向新记录，不删除。

## 读写权限

| 角色 | 可写 | 只读 |
|---|---|---|
| 员工 | 自己的 worker 记录；自己产出的文件（新建、补充、建议等级） | 自己的文件结论 |
| 项目管家 | 本项目的全部 worker 与 file 记录；等级判定；L1 结论；L2 上报 | 其他项目 |
| 大总管 | 用户的事项（只建需要人做的，遵守事项拆分门）、文件的 `decision`（只转写用户原话，标 `decided_by: user`） | 所有项目的 worker 与 file |
| 用户 | 任何记录 | — |

大总管转写用户批复时必须保留原话，不总结、不改写、不补充专业判断；用户只说“同意”时就记“同意”。
