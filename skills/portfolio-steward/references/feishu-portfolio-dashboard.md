# 大总管飞书多维表格方案

## 目标与推荐时机

飞书多维表格用于让用户和协作者清楚看到：有哪些子仓库、哪些通用进化候选待审、哪一批母版待批准、哪些子仓库尚未同步。

满足以下任一条件时主动建议启用：

- 同时管理至少两个活跃子仓库；
- evolution proposal 需要跨天审查、去重或多人协作；
- 用户需要在手机上集中查看“待我决定”“待发布”“待同步”；
- HTML 总览已经能看，但负责人、筛选、提醒和状态流转不够清晰。

普通飞书电子表格适合计算型数据；这里需要关联记录、人员字段、视图和工作流，默认选择 Base。用户拒绝或没有回复时继续维护文件与 HTML，不重复推荐。

建议用语：

> 现在已经有多个仓库子管家和跨仓库候选，仅靠 HTML 适合看总览，但负责人、待审核和待同步队列不够好管理。我建议启用飞书多维表格做协作控制面：手机可查，可按仓库、状态和负责人筛选，待你决定的事项也能集中显示；HTML 继续保留为只读总览。如果你同意，请给我现有 Base 链接，或授权我新建一份。

## 三层事实边界

| 层 | 职责 | 不承担 |
|---|---|---|
| `.steward/`、registry、harvest report | lineage、core hash、proposal 原文、drift 与同步诊断的机器 SSOT | 人员协作体验 |
| 飞书 Base | 负责人、审查队列、建议结论、用户决定、发布与同步跟踪 | 重写或伪造机器事实 |
| HTML 看板 | 跨仓库总览、趋势和证据链接的只读快照 | 独立编辑状态 |

Base 中的 lineage、hash、proposal 摘要必须来自 harvest / status 输出。Base 中形成的审查结论和用户决定必须回写到 proposal、发布记录或仓库内决策文档，再刷新 HTML。HTML 显示 Base 链接、数据基线与最后同步时间。

## Base 结构

使用一个 Base、4 张核心表；需要完整事件审计时再增加第 5 张日志表。所有 ID 都使用稳定文本键并通过 upsert 更新，不能按名称模糊匹配。

### 1. 子仓库（Repositories）

| 字段 | 类型 | 内容 |
|---|---|---|
| Repository ID | 文本 | 唯一键，不因显示名变化而改变 |
| 仓库 | 文本 | 用户可读名称 |
| 仓库 / 文档链接 | 超链接 | 可公开或已授权的稳定入口 |
| 子管家 Skill | 文本 | 实际安装位置或相对路径 |
| 负责人 | 人员 | 子仓库管家或人工负责人 |
| 母版基线版本 | 文本 | lineage 中的 source version / commit |
| Base Core Hash | 文本 | 当前三方同步基线 |
| 当前 Core Hash | 文本 | status / harvest 读取结果 |
| Drift 状态 | 单选 | 无漂移 / 本地修改 / 上游可升级 / 双边冲突 / 未知 |
| Local 规则状态 | 单选 | 正常 / 缺失 / 待检查；不上传私有正文 |
| 待审候选数 | Lookup / 数字 | 关联“进化候选”汇总 |
| 同步状态 | 单选 | 已同步 / 待同步 / 同步中 / 冲突 / 暂缓 |
| 下一动作 | 多行文本 | 谁做什么 + 停止条件 |
| 最后巡检 | 日期时间 | 最近一次 status / harvest 时间 |
| 证据 | 超链接 | status 或 harvest 报告 |

### 2. 进化候选（Evolution Proposals）

| 字段 | 类型 | 内容 |
|---|---|---|
| Proposal ID | 文本 | 对应 `EV-*.json` 的稳定 ID |
| 来源仓库 | 关联记录 | 关联“子仓库” |
| Scope | 单选 | local / upstream_candidate |
| 失败与根因 | 多行文本 | 脱敏摘要，原文仍以 proposal 为准 |
| 规则变更 | 多行文本 | 候选摘要 |
| 证据 / 验证 | 多行文本 + 超链接 | 可追溯证据与验证结果 |
| 隐私审查 | 单选 | 未检查 / 通过 / 不通过 |
| 去重组 | 文本 | 相同或相关候选的归并键 |
| 审查状态 | 单选 | 待初审 / 补证据 / 重复 / 拒绝 / 建议合入 / 已进入发布 / 已发布 |
| 大总管建议 | 多行文本 | 结论、理由和影响面 |
| 影响仓库 | 关联记录 | 关联一个或多个子仓库 |
| 负责人 | 人员 | 当前审查责任人 |
| 用户决定 | 单选 | 不适用 / 待决定 / 批准 / 拒绝 / 暂缓 |
| PR / 报告 | 超链接 | 可审阅交付物 |
| 最后更新 | 修改时间 | 系统字段 |

### 3. 母版发布（Template Releases）

字段：发布 ID / 版本、状态（草拟 / 待用户批准 / 已批准 / 已发布 / 已撤回）、关联候选、母版 commit、影响说明、验证摘要、用户决定、PR、发布时间、发布说明。只有用户批准的候选才能进入“已发布”；Base workflow 不得自动批准或合并。

### 4. 子仓库同步（Child Sync Runs）

字段：Sync ID、关联仓库、来源版本、目标版本、同步状态（待运行 / 运行中 / 成功 / 冲突 / 暂缓 / 失败）、三方基线、冲突数量、`references/local/` 排除检查、执行负责人、开始 / 完成时间、status / drift 报告、下一动作。一次同步一条记录，不覆盖历史 run。

### 5. 事件与决定（可选，只追加）

当需要完整审计时记录：时间、关联仓库 / 候选 / 发布 / 同步、事件类型、变更前、变更后、原因、操作者、用户决定与证据链接。更正通过追加记录完成，不篡改旧事件。

## 默认视图

1. **组合总览**：所有活跃子仓库，按 Drift 状态和同步状态分组。
2. **待审候选**：`upstream_candidate` 且未形成终态，按隐私审查、证据完整度排序。
3. **待用户决定**：候选或发布批次的用户决定为“待决定”。
4. **建议合入**：已通过脱敏、证据、去重与验证审查的候选。
5. **已发布待同步**：母版已经发布，但关联子仓库仍为待同步 / 冲突。
6. **同步冲突**：只看三方同步冲突、local 排除失败或执行失败。
7. **本月完成**：已发布候选和成功同步记录，按完成时间倒序。
8. **负责人视图**：按人员过滤其当前待审、待同步和阻塞项。

## 提醒与自动化边界

- 可提醒：待用户决定、审查逾期、发布后仍未同步、同步冲突超过约定时限。
- 不自动执行：批准候选、合并 PR、发布母版、向子仓库应用三方同步。
- workflow 最多把材料齐全的候选推进到“待大总管审查”，不能自动写“建议合入”。
- 对外发送飞书通知前，先获得通知对象与频率授权；没有变化时不重复提醒。

## 启用流程

1. 说明 Base、机器事实与 HTML 的分工，取得用户明确同意。
2. 请用户提供现有 Base 链接，或授权新建；认证 / scope 问题按 `lark-shared` 处理。
3. 完整读取 `lark-base` Skill，先读取真实 Base 结构，再创建或对齐表、字段、选项与视图。
4. 先导入一个子仓库、一个候选和一次同步样例，验证关联、权限与用户可见性。
5. 使用 registry + harvest 批量 upsert；不把 `references/local/` 私有正文上传飞书。
6. 将 Base 链接、数据基线和最后同步时间写入 HTML；告知用户协作控制面已启用，但机器 SSOT 没有迁移。
